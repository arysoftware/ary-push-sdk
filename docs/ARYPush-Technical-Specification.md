## 1. Architectural & Configuration Standard

ARYPush is a push notification SDK for native Android, native iOS and Flutter applications,
backed by a project-scoped REST API. The SDK owns the device side of the push lifecycle —
permission, token, token refresh, notification display, tap handling and synchronisation — and
reports device state to the backend through **exactly five endpoints**.

### 1.1 Configuration model

The host application supplies four values when it initializes the SDK. Nothing is hardcoded in
the SDK, so one build works against any environment.

| Value | Purpose | Android / Flutter | iOS |
| --- | --- | --- | --- |
| Base URL | Root of the push API, e.g. `https://easypanel.host` | `baseUrl` | `baseURL` |
| Application ID | Public label identifying the app. **Not a credential** | `applicationId` | `applicationId` |
| Project ID | Scopes every request to a project | `projectId` | `projectId` |
| Auth token | Bearer token sent on every request | `authToken` | `authToken` |

All four live in `PushBackendConfig`, passed as the `backend` of `ARYPushConfig`. iOS spells the
base URL `baseURL` in keeping with Swift naming conventions; the meaning is identical.

**The base URL is used exactly as the app passes it.** The SDK adds no version segment — no `/v1`,
nothing — and there is no API-version setting. Each endpoint path is joined straight onto it:

| Base URL passed in | Register Device is sent to |
| --- | --- |
| `https://easypanel.host` | `https://easypanel.host/api/notifications/devices/register?projectId=…` |
| `https://easypanel.host/` | the same — a trailing slash is ignored |
| `https://easypanel.host/push` | `https://easypanel.host/push/api/notifications/devices/register?projectId=…` |

So the base URL comes straight from the app's own build configuration, and a deployment that
serves the API under a path prefix just includes that prefix in the base URL.

Omitting `backend` entirely is supported: push notifications are still received and displayed,
and no request is ever made to a server.

### 1.2 Request conventions

Every request the SDK makes follows these rules.

| Rule | Value |
| --- | --- |
| Authentication header | `Authorization: Bearer {{bearer_token}}` — a device key, e.g. `Authorization: Bearer ary_device_key_xxxxxxxxxxxxxxxxxxxxxxxx` |
| Content type | `Content-Type: application/json` on requests with a body |
| Project scope | `projectId={{project_id}}` query parameter on **every** request |
| Core identifier | `installationId` — a persistent UUID generated by the SDK on first launch |
| Transport | HTTPS. Plain HTTP is accepted only for local testing |
| Encoding | UTF-8 JSON request and response bodies |

`projectId` is appended by the transport layer rather than by each call, so it cannot be
forgotten on a new endpoint.

### 1.3 Additional headers

The SDK also sends these headers. They are informational: the backend may log or ignore them,
but must not require any of them.

| Header | Example | Use |
| --- | --- | --- |
| `Accept` | `application/json` | Content negotiation |
| `X-Application-Id` | `wallet_android` | Same value as `applicationId` |
| `X-Installation-Id` | `8f14e45f-…` | Correlation and logging |
| `X-Platform` | `android`, `ios` | Triage |
| `X-SDK-Version` | `1.1.0` | Compatibility triage |
| `X-App-Version` | `5.2.0` | Compatibility triage |
| `X-Request-ID` | UUID | Stable across retries of one logical request — ideal for idempotency and log correlation |

### 1.4 Identifiers

Three identifiers describe a device. Keeping them distinct is the backend's most important data
modelling decision.

| Identifier | Identifies | Changes when | Sent to the backend |
| --- | --- | --- | --- |
| **`installationId`** | One app on one device | Never — only on reinstall | Yes, in every relevant body |
| **Push `token`** | A delivery route (FCM or APNs) | Whenever the OS decides: reinstall, restore, data clear | Yes |
| User ID | A person | Login and logout | **No** — kept on the device only |

A device whose token rotates keeps its `installationId`. The backend should key installation
records on `installationId` and treat `token` as a mutable attribute of that record.

### 1.5 What the backend does not receive

The SDK has capabilities with no corresponding endpoint. They work fully on the device and are
**never** sent to the server:

| Capability | SDK API | Behaviour |
| --- | --- | --- |
| User identity | `login(userId)`, `logout()` | Stored locally |
| Tags | `addTags(...)`, `removeTags(...)` | Stored locally |
| Topics | `subscribeToTopic(...)` | **Android:** works — FCM delivers to the topic from the device's own subscription. **iOS:** recorded on the device only. APNs has no topics, and with no topics endpoint the backend cannot fan out, so an iOS topic subscription does not affect delivery. Use segments instead |
| Engagement events | automatic `notification_received` / `notification_opened` | Not transmitted |

Adding any of these to the server later is an additive change: see section 11.2.

## 2. API Mapping & Reference Table

| # | Operation | Method | Path | Query | Success | Triggered by |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Register Device | `POST` | `/api/notifications/devices/register` | `projectId` | `200` / `201` | First launch; any change to the installation |
| 2 | Device Token Update | `PUT` | `/api/notifications/devices/update` | `projectId` | `200` / `204` | Push token refresh |
| 3 | Subscribe / Unsubscribe | `PUT` | `/api/notifications/devices/toggle` | `projectId` | `200` / `204` | Notification permission change |
| 4 | Add Segment Subscriber | `POST` | `/api/segments/{segmentId}/subscribers` | `projectId` | `200` / `201` | App calls `subscribeToSegment(id)` |
| 5 | Segment List | `GET` | `/api/segments/list` | `projectId` | `200` | App calls `getSegments()` |

### 2.1 Expected status codes

| Status | Meaning | SDK behaviour |
| --- | --- | --- |
| `200`, `201`, `204` | Success | Operation complete |
| `400` | Malformed request | Permanent — dropped, not retried |
| `401` | Missing or invalid bearer token | Permanent with a static `authToken`; one refresh-and-retry with an `AuthProvider` |
| `403` | Token valid, access to project denied | Permanent — dropped |
| `404` | Unknown project, segment or path | Permanent — dropped |
| `409` | Conflict | Permanent — dropped |
| `422` | Validation failed (e.g. unknown `applicationId`) | Permanent — dropped |
| `408`, `425`, `429` | Timeout, too early, rate limited | Retried with backoff |
| `5xx` | Server error | Retried with backoff |

**The status code drives the SDK's retry policy.** A transient failure returned as `4xx` is
dropped permanently; a permanent failure returned as `5xx` is retried until the attempt budget is
exhausted. See section 4.

### 2.2 Error body

Any of these shapes is understood. The message is logged by the SDK; it is never shown to users.

```json
{ "error": { "code": "invalid_project", "message": "Project not found" } }
```

```json
{ "code": "invalid_project", "message": "Project not found" }
```

## 3. Endpoint Reference

### 3.1 Register Device

```
POST /api/notifications/devices/register?projectId={{project_id}}
```

Creates or refreshes the installation record.

**Request body**

```json
{
  "token": "dGhpcyBpcyBhIHRva2Vu...",
  "platform": "android",
  "applicationId": "wallet_android",
  "installationId": "8f14e45f-ea1e-4f7a-b2c1-5b2d7a1c9e33",
  "provider": "fcm",
  "appVersion": "5.2.0",
  "appBuild": "520",
  "sdkVersion": "1.1.0",
  "notificationsEnabled": true,
  "device": {
    "osVersion": "14",
    "deviceModel": "Google Pixel 8",
    "locale": "en-PK",
    "timezone": "Asia/Karachi"
  }
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `token` | string \| null | No | FCM registration token or APNs device token. Absent or `null` before the OS has issued one |
| `platform` | string | Yes | `android` or `ios` |
| `applicationId` | string | Yes | Public application label |
| `installationId` | string (UUID) | Yes | **Upsert key** |
| `provider` | string | Yes | `fcm` or `apns` — which transport issued `token` |
| `appVersion` | string | No | Host app version name |
| `appBuild` | string | No | Host app build number |
| `sdkVersion` | string | Yes | ARYPush SDK version |
| `notificationsEnabled` | boolean | Yes | Whether the OS currently permits notifications |
| `device` | object | No | **Absent entirely** when the host app disabled device-info collection |
| `device.osVersion` | string | No | e.g. `14`, `17.4` |
| `device.deviceModel` | string | No | e.g. `Google Pixel 8`, `iPhone16,1` |
| `device.locale` | string | No | BCP-47, e.g. `en-PK` |
| `device.timezone` | string | No | IANA, e.g. `Asia/Karachi` |

**Backend requirements**

- **Upsert on `installationId`.** The SDK re-sends Register whenever any field changes —
  including events that change nothing in this body, such as login — so repeated identical calls
  must not create duplicate records.
- **Treat a missing field and a `null` field identically.** Android sends `null`; iOS omits the
  key. Both mean "no value".
- **One live token per device.** A token can move between installations after a device restore.
  When a Register arrives carrying a token already held by a *different* installation, clear it
  from the older one, or that device receives every message twice.

| Status | When |
| --- | --- |
| `200` / `201` | Registered or refreshed |
| `400` | Malformed body |
| `401` | Bearer token missing or invalid |
| `422` | Unknown `applicationId`, or a token the provider rejects |

<div style="page-break-after: always;"></div>

### 3.2 Device Token Update

```
PUT /api/notifications/devices/update?projectId={{project_id}}
```

Replaces the push token held for an installation.

**Request body**

```json
{
  "installationId": "8f14e45f-ea1e-4f7a-b2c1-5b2d7a1c9e33",
  "newToken": "bmV3IHRva2Vu...",
  "platform": "android",
  "notificationsEnabled": true,
  "appVersion": "5.2.0"
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `installationId` | string (UUID) | Yes | Installation whose token changed |
| `newToken` | string | Yes | The replacement token |
| `platform` | string | Yes | `android` or `ios` |
| `notificationsEnabled` | boolean | No | Current OS permission state |
| `appVersion` | string | No | Host app version name |

**Backend requirements**

- Idempotent: applying the same `newToken` twice leaves the record unchanged.
- The SDK always sends a Register carrying the same new token **before** this call, so the
  installation is guaranteed to exist. Returning `404` for an unknown `installationId` is
  therefore safe, and the operation is dropped rather than retried.

| Status | When |
| --- | --- |
| `200` / `204` | Updated |
| `404` | Unknown `installationId` |
| `422` | Token rejected by the provider |

### 3.3 Subscribe / Unsubscribe

```
PUT /api/notifications/devices/toggle?projectId={{project_id}}
```

Records whether the operating system currently permits notifications for a device.

**Request body**

```json
{
  "token": "dGhpcyBpcyBhIHRva2Vu...",
  "notificationsEnabled": false
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `token` | string | Yes | Current push token — the device key for this endpoint |
| `notificationsEnabled` | boolean | Yes | `true` = subscribed, `false` = unsubscribed |

**Backend requirements**

- Look the device up by `token`.
- The SDK never sends this before the device has a token. The Register sent when the token
  arrives already carries `notificationsEnabled`, so nothing is lost by that.
- Suppress sends to devices where this is `false`: it keeps delivery metrics honest and avoids
  paying to send messages that cannot be displayed.

The permission can change without the app being told — a user turning notifications off in system
Settings produces no callback. The SDK samples the state every time the app comes to the
foreground and sends this call when it differs from the last value reported.

| Status | When |
| --- | --- |
| `200` / `204` | Recorded |
| `404` | Unknown token |

### 3.4 Add Segment Subscriber

```
POST /api/segments/{segmentId}/subscribers?projectId={{project_id}}
```

Adds an installation to a segment.

**Path parameter**

| Parameter | Description |
| --- | --- |
| `segmentId` | Segment identifier, as returned by Segment List. Percent-encoded by the SDK |

**Request body** — the full installation payload, identical in shape to Register Device
(section 3.1):

```json
{
  "token": "dGhpcyBpcyBhIHRva2Vu...",
  "platform": "ios",
  "applicationId": "wallet_ios",
  "installationId": "3c9d2a7e-1f4b-4d8e-9a6c-7b2e5f1d0c84",
  "provider": "apns",
  "appVersion": "5.2.0",
  "appBuild": "520",
  "sdkVersion": "1.1.0",
  "notificationsEnabled": true,
  "device": {
    "osVersion": "17.4",
    "deviceModel": "iPhone16,1",
    "locale": "en-PK",
    "timezone": "Asia/Karachi"
  }
}
```

**Backend requirements**

- **Adding an existing subscriber should succeed with `2xx`.** The SDK treats `409` as a failure
  and reports `false` to the application, which would present a device that *is* subscribed as
  having failed.
- Upsert the installation from the payload if it is not yet known.

This call is **not queued**. It is made only when the application calls
`subscribeToSegment(segmentId)`, and its result is returned to the application directly, so it
fails while offline rather than reporting an optimistic success.

| Status | When |
| --- | --- |
| `200` / `201` | Subscribed, or already subscribed |
| `404` | Unknown segment |
| `422` | Invalid installation payload |

### 3.5 Segment List

```
GET /api/segments/list?projectId={{project_id}}
```

Returns the segments defined for the project. No request body.

**Response** — any of these shapes is accepted:

```json
[
  {
    "id": "seg_premium_pk",
    "name": "Premium Pakistan Users",
    "description": "subscription == premium AND country == PK",
    "joinedAt": 1730000000000
  }
]
```

```json
{ "segments": [ { "id": "seg_premium_pk", "name": "Premium Pakistan Users" } ] }
```

```json
{ "data": [ { "segmentId": "seg_premium_pk", "name": "Premium Pakistan Users" } ] }
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` or `segmentId` | string | Yes | Entries without one are skipped |
| `name` | string | No | Defaults to the id |
| `description` | string | No | |
| `joinedAt` | number | No | Epoch milliseconds |

This is the **project's segment catalogue**, not the segments a particular device belongs to.
The SDK does not cache it: a call is made each time the application asks.

| Status | When |
| --- | --- |
| `200` | Segment list, possibly empty |

## 4. Response Handling & Retry Semantics

Registration, token updates and toggles are written to a **durable queue** on the device. They
survive app restarts and airplane mode, and are delivered once connectivity returns. Segment
subscription and the segment list are direct calls whose results go straight to the application.

### 4.1 Retry policy

| Condition | Behaviour |
| --- | --- |
| `2xx` | Success |
| `400`, `403`, `404`, `409`, `422` | Permanent. The operation is dropped and never retried |
| `401` with a static `authToken` | Permanent |
| `401` with an `AuthProvider` | One token refresh, then exactly one retry. Never loops |
| `408`, `425`, `429`, `5xx`, network error | Retried with exponential backoff and full jitter |
| `2xx` whose body cannot be parsed | Permanent — a malformed success is a contract violation |

`Retry-After` is honoured on retryable responses, in seconds or as an HTTP date, capped at
15 minutes so that a mistaken header cannot stall a device's queue.

### 4.2 Two rules for the backend

1. **Never return `4xx` for a transient failure.** A database timeout, an unavailable dependency or
   a deployment in progress must be `5xx`. A `4xx` tells the SDK to give up permanently.
2. **Never return `5xx` for a permanent rejection.** An unknown `applicationId` or a malformed body
   must be `4xx`. A `5xx` makes the SDK retry a request that can never succeed.

Both mistakes cause silent data loss: no error is visible anywhere.

### 4.3 Idempotency

Every queued request may be delivered **more than once**. Registration is an upsert keyed on
`installationId`; token updates and toggles are replacements. `X-Request-ID` is stable across all
retries of one logical request and can be used to deduplicate.

## 5. When the SDK Calls Each Endpoint

| Event on the device | Requests, in order |
| --- | --- |
| First launch, no token yet | 1. Register (`token` absent) |
| First token issued | 1. Register (with token) · 2. Token Update |
| Token refreshed by the OS | 1. Register (new token) · 2. Token Update |
| User turns notifications off in Settings, reopens app | 1. Register (`notificationsEnabled: false`) · 2. Toggle |
| App updated to a new version | 1. Register (new `appVersion`) |
| User logs in or out | 1. Register (body unchanged) |
| Relaunch with nothing changed | *No request* — the SDK hashes the record and skips unchanged registrations |
| App calls `subscribeToSegment(id)` | Add Segment Subscriber |
| App calls `getSegments()` | Segment List |

Register always precedes Token Update and Toggle for the same device state, so those two calls
never arrive for an installation the backend has not been told about.

## 6. Sending Notifications

The backend holds the delivery credentials and sends through Firebase Cloud Messaging (Android,
and iOS apps that use Firebase) or APNs (iOS). **No credential ever ships inside the mobile app.**

| Platform | Credential | Where it lives |
| --- | --- | --- |
| Android | FCM service account (HTTP v1 API) | Backend secret store |
| iOS | APNs authentication key (`.p8`) or certificate | Backend secret store |

Route each message by the device's `provider`: an FCM token sent through APNs, or the reverse,
reaches nobody.

### 6.1 Send data-only messages

A data-only message is the only shape that behaves identically in the foreground, in the
background and when the app is terminated, on both platforms. A message with a `notification`
block is displayed by the operating system before the SDK sees it, which loses deduplication,
action buttons and tap tracking.

- **FCM:** send only the `data` object; omit `notification`.
- **APNs:** set `content-available: 1` and place the keys below in the payload.

### 6.2 Payload keys

```json
{
  "ary_push": "1",
  "notification_id": "order-42",
  "title": "Order shipped",
  "body": "Your order is on its way",
  "image_url": "https://cdn.ary.com/order.png",
  "channel_id": "orders",
  "url": "https://ary.com/orders/12345",
  "action": "open_order",
  "orderId": "12345",
  "actions": "[{\"id\":\"track\",\"title\":\"Track\"}]"
}
```

| Key | Purpose |
| --- | --- |
| `ary_push` | Marks the message as ARYPush's, so an app with its own messaging code can tell them apart |
| `notification_id` | **Stable message identity — always send it.** Enables deduplication across resends |
| `title`, `body` | Notification content |
| `image_url` | Large image |
| `channel_id` | Android notification channel; falls back to the SDK default if unknown |
| `url`, `deep_link`, `link`, `launch_url` | **Opened automatically when the notification is tapped.** The first one present wins, in that order |
| `action` and custom keys | Passed verbatim to the app's tap handler, which decides where to navigate |
| `actions` | Action buttons, as a **JSON-encoded string** |

### Links

A payload carrying `url`, `deep_link`, `link` or `launch_url` is opened by the SDK itself on tap,
in every app state — foreground, background and terminated. The first key present wins, in that
order. Send an absolute URL: a universal or App Link (`https://…`) or a scheme the app registers
(`myapp://order/42`).

- If the application itself can handle the link, it opens **inside the app**. On Android the SDK
  tries the host application before anything else, so the user never sees a chooser.
- Otherwise the system decides, which for a plain web link means the browser.
- A link with no scheme is ignored and the app is simply brought forward.
- Only a tap on the notification body opens it. Action buttons stay host-handled, since `actions`
  mean something specific the app defined.

`ARYPush.onNotificationOpened` still fires either way, carrying the same payload, so an app that
would rather route the link itself can keep doing so — the value is on the notification as
`launchUrl`. Beyond that link the SDK does not navigate: the set of `action` values is a contract
between the campaigns that send them and the app code that handles them.

### 7.2 Initialization — `Application.onCreate`

```kotlin
package com.example.wallet

import android.app.Application
import com.ary.push.ARYPush
import com.ary.push.ARYPushConfig
import com.ary.push.PushBackendConfig
import com.ary.push.PushLogLevel

class WalletApplication : Application() {

    override fun onCreate() {
        super.onCreate()

        ARYPush.initialize(
            this,
            ARYPushConfig(
                enableLogging = true, // set to false for release builds
                logLevel = PushLogLevel.DEBUG,
                backend = PushBackendConfig(
                    baseUrl = "https://easypanel.host",
                    applicationId = "wallet_android",
                    projectId = "YOUR_PROJECT_ID",
                    authToken = "ary_device_key_xxxxxxxxxxxxxxxxxxxxxxxx"
                )
            )
        )

        // Registered here rather than in an Activity: a tap that launched the app from a
        // terminated state is replayed to the first listener, and no Activity exists yet.
        ARYPush.addNotificationOpenedListener { notification ->
            NotificationRouter.route(this, notification)
        }
    }
}
```

Register the class in `AndroidManifest.xml`:

```xml
<application
    android:name=".WalletApplication"
    ... >
```

The SDK's messaging service, tap handler and permissions arrive through manifest merging — no
other manifest entries are needed.

### 7.3 Notification click listener

```kotlin
package com.example.wallet

import android.content.Context
import android.content.Intent
import com.ary.push.model.PushNotification

object NotificationRouter {

    fun route(context: Context, notification: PushNotification) {
        val intent = when (notification.action) {
            "open_order" -> Intent(context, OrderActivity::class.java)
                .putExtra("orderId", notification.data["orderId"])
            else -> Intent(context, MainActivity::class.java)
        }
        context.startActivity(intent.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK))
    }
}
```

`notification.actionId` is set when the user tapped an action button rather than the
notification itself.

### 7.4 Permission and segments

```kotlin
// Android 13+: ask at a moment the user understands why.
ARYPush.requestPermission { status -> /* update UI */ }

// Segment list and subscription.
ARYPush.getSegments { segments ->
    val premium = segments.firstOrNull { it.name == "Premium Pakistan Users" }
    if (premium != null) {
        ARYPush.subscribeToSegment(premium.id) { subscribed -> /* ... */ }
    }
}
```

Suspending forms of `getSegments()` and `subscribeToSegment(id)` are available inside coroutines.

### 7.5 Changing the token after login

Call `initialize` again with the new token; the SDK reconfigures in place and keeps its queue,
listeners and installation id. `pushConfig` is the `ARYPushConfig` the app initialized with:

```kotlin
fun onUserSignedIn(context: Context, pushConfig: ARYPushConfig, newToken: String) {
    ARYPush.initialize(
        context,
        pushConfig.copyWith(backend = pushConfig.backend?.copy(authToken = newToken))
    )
}
```

For tokens that expire, supply an `AuthProvider` (`ARYPushConfig(authProvider = ...)`) instead.
It is asked for a token on every request, can refresh once on `401`, and takes precedence over
the static `authToken`.

## 8. SDK Integration — iOS (Swift)

**Requirements:** iOS 13, Xcode 15, Swift 5.9.

### 8.1 Swift Package Manager

1. In Xcode, choose **File › Add Package Dependencies…**
2. Enter `https://github.com/arysoftware/ary-push-sdk`
3. Set **Dependency Rule** to *Branch* `main` — or, once release `v1.1.0` is tagged,
   *Up to Next Major Version* from `1.1.0`
4. Add the **ARYPush** library to your app target.

The repository is public: no GitHub account needs to be signed in to Xcode. Or declare it in a
`Package.swift`:

```swift
dependencies: [
    // Swap for `from: "1.1.0"` once that release is tagged.
    .package(url: "https://github.com/arysoftware/ary-push-sdk.git", branch: "main")
],
targets: [
    .target(name: "YourApp", dependencies: [
        .product(name: "ARYPush", package: "ary-push-sdk")
    ])
]
```

### 8.2 Capabilities — required

Under the app target's **Signing & Capabilities**:

1. **+ Capability › Push Notifications.** Without it iOS issues no device token at all.
2. **+ Capability › Background Modes**, then tick **Remote notifications** (for background and
   silent messages).

Test on a physical device: the iOS Simulator never receives an APNs device token.

### 8.3 Initialization — `AppDelegate`

```swift
import UIKit
import ARYPush

@main
final class AppDelegate: UIResponder, UIApplicationDelegate {

    var window: UIWindow?

    func application(
        _ application: UIApplication,
        didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
    ) -> Bool {

        ARYPush.initialize(
            ARYPushConfig(
                enableLogging: true,
                logLevel: .debug,
                backend: PushBackendConfig(
                    baseURL: "https://easypanel.host",
                    applicationId: "wallet_ios",
                    projectId: "YOUR_PROJECT_ID",
                    authToken: "ary_device_key_xxxxxxxxxxxxxxxxxxxxxxxx"
                )
            )
        )

        // Registered during launch so a tap that launched the app from a terminated state is
        // replayed to this listener rather than lost.
        ARYPush.addNotificationOpenedListener { notification in
            NotificationRouter.route(notification)
        }

        return true
    }
}
```

No other `AppDelegate` code is needed. The SDK registers with APNs, receives the device token and
installs its notification-centre delegate automatically. An existing
`UNUserNotificationCenterDelegate` keeps working: the SDK forwards to it rather than replacing it.

### 8.4 Notification tap handling

```swift
import ARYPush

enum NotificationRouter {

    static func route(_ notification: PushNotification) {
        switch notification.action {
        case "open_order":
            AppNavigator.shared.openOrder(id: notification.data["orderId"])
        default:
            AppNavigator.shared.openHome()
        }
    }
}
```

The listener is called on the main queue. `notification.actionId` is set when an action button
was tapped.

### 8.5 Permission and segments

```swift
ARYPush.requestPermission { status in
    // update UI
}

Task {
    let segments = await ARYPush.getSegments()
    if let premium = segments.first(where: { $0.name == "Premium Pakistan Users" }) {

        print("Subscribed: \(subscribed)")
    }
}
```

### 8.6 Firebase Messaging on iOS

iOS gives the SDK an **APNs device token** (`provider: apns`). If your backend sends to iOS through
Firebase instead, hand the SDK the FCM registration token so it registers that one:

```swift
func messaging(_ messaging: Messaging, didReceiveRegistrationToken fcmToken: String?) {
    if let fcmToken { ARYPush.setFCMToken(fcmToken) }
}
```

```dart
  // replayed to this listener rather than lost.
```

### 9.3 `ARYPush.onNotificationOpened` listener

```dart
void _routeNotification(PushNotification notification) {
  final NavigatorState? navigator = navigatorKey.currentState;
  if (navigator == null) return;

  switch (notification.action) {
    case 'open_order':
      navigator.pushNamed('/order', arguments: notification.data['orderId']);
    default:
      navigator.pushNamed('/');
  }
}
```

### 9.4 Permission, token and segments

```dart
final PushPermissionStatus status = await ARYPush.requestPermission();

// The token arrives asynchronously -- on iOS after a round trip to Apple -- so listen rather
// than reading it once immediately after initialize().
ARYPush.onTokenRefresh.listen((String token) => debugPrint('Push token: $token'));

final List<Segment> segments = await ARYPush.getSegments();
final bool subscribed = await ARYPush.subscribeToSegment(segments.first.id);
```

### 9.5 Changing the token after login

Flutter has no `AuthProvider`; call `initialize` again with the new token. The SDK reconfigures in
place and keeps its queue, listeners and installation id:

```dart
await ARYPush.initialize(
  ARYPushConfig(
    backend: PushBackendConfig(
      baseUrl: 'https://easypanel.host',
      applicationId: 'wallet_flutter',
      projectId: 'YOUR_PROJECT_ID',
      authToken: newToken,
    ),
  ),
);
```

### 9.6 iOS with Firebase Messaging

If your backend sends to iOS through Firebase, pass the FCM token on. It is ignored on Android,
so this can live in shared code:

```dart
FirebaseMessaging.instance.onTokenRefresh.listen(ARYPush.setFCMToken);
final String? fcmToken = await FirebaseMessaging.instance.getToken();
if (fcmToken != null) await ARYPush.setFCMToken(fcmToken);
```

## 11. Appendix — Security, Versioning and Compatibility

### 11.1 Security

| Rule | Detail |
| --- | --- |
| `applicationId` is not a credential | It is compiled into the app and readable by anyone. It must never authorize anything |
| The bearer token is never logged | The SDK excludes `Authorization` from logs at every level, and masks `authToken` when a configuration is printed |
| No token in `Info.plist` | iOS reads `ProjectId` from `Info.plist` but deliberately not the token: that file ships in the app as plain text |
| No delivery credentials in the app | FCM service accounts and APNs keys live only in the backend's secret store |
| TLS | Production traffic is HTTPS only. The SDK never disables certificate validation |

A bearer token passed to the SDK is present in the device's memory for as long as the SDK runs.
Issue a token scoped to device registration only, rather than reusing a user's full-access token.

### 11.2 Versioning

- **Additive changes** — a new optional field, a new endpoint — are compatible with every SDK in
  the field.
- **Breaking changes** — removing or renaming a field, changing a type, changing what a status code
  means, or moving a path — need a new path served alongside the old one.

A released mobile app cannot be made to update on the backend's schedule. Assume old SDK versions
remain in use for at least a year, and that some devices never update.

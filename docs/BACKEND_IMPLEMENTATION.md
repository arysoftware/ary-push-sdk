# Building the ARY Push backend

A step-by-step build order for the team implementing the server side.

[REST_API.md](REST_API.md) is the contract and [BACKEND.md](BACKEND.md) is the data model. This
document is the plan: what to build, in what order, and how to know each step is finished. Where
the two disagree, **REST_API.md wins** — the mobile SDK is already written against it and is in
the field.

## What you are building

A service that keeps a register of app installations, records what the client tells it about
them, decides which of them a given message should reach, and sends it through FCM and APNs.

```
SDK  ──►  your API  ──►  FCM / APNs  ──►  device
              │
              ├── installations, users, tokens
              ├── tags        (client sends)
              ├── segments    (you compute)
              └── campaigns, delivery, reporting
```

**The SDK sends attributes; you decide what they mean.** It never evaluates a segment rule, never
holds a credential, and never decides who receives a campaign. That boundary is deliberate:
targeting rules change weekly, and a released app takes months to fully adopt.

### Not in scope for the SDK, therefore yours

Campaign management, scheduling, the dashboard, delivery reporting, and the FCM/APNs credentials
themselves. None of it exists client-side and none of it should.

---

## Before you write any code

Four decisions block everything else. Make them first.

| Decision | Why it blocks | Default if you have no strong view |
| --- | --- | --- |
| **Environments** | The app hardcodes nothing; each env needs its own URL, apps, installations and provider credentials | `dev`, `qa`, `staging`, `prod`, fully separate |
| **`applicationId` registry** | Every request carries one; unknown values must be rejected with 422 | One per app per platform, e.g. `wallet_android`, `wallet_ios` |
| **Authentication** | The SDK sends `Authorization: Bearer <token>` only if the host app configures an `AuthProvider`. Decide whether you require it | Require it in prod; allow anonymous in dev |
| **Datastore** | Everything below assumes relational; document stores work but the uniqueness rules get harder | PostgreSQL |

> **`applicationId` is a public label, not a credential.** It ships inside the APK and IPA and can
> be read by anyone who unzips them. Never let it authorise anything. If you need to authenticate
> the caller, that is what the `Authorization` header is for.

## Step 1 — Schema

Build this before any endpoint. Every later step assumes it.

The three identifiers below are the single most important thing to get right. Conflating any two
of them causes bugs that only appear in production, on real devices, weeks later.

| Identifier | Identifies | Changes when |
| --- | --- | --- |
| **Installation ID** | One app on one device | Never — reinstall or explicit reset only |
| **Push token** | A delivery route | Whenever the transport decides: reinstall, restore, data clear |
| **User ID** | A person | Login and logout |

A person with a phone and a tablet is **one user, two installations**. A device whose token
rotates keeps its installation id, its tags and its history. A device whose user logs out keeps
everything except the user association.

### Tables

```sql
applications      id TEXT PK              -- 'wallet_android'; what the SDK sends
                  platform TEXT           -- 'android' | 'ios'
                  -- FCM/APNs credentials belong in your secret store, not here

users             id TEXT PK              -- the host application's own user id
                  application_id TEXT FK

installations     id UUID PK              -- generated by the SDK, never by you
                  application_id TEXT FK NOT NULL
                  user_id TEXT FK NULL    -- NULL when logged out
                  platform TEXT NOT NULL
                  provider TEXT NOT NULL  -- 'fcm' | 'apns'
                  push_token TEXT NULL
                  app_version TEXT, app_build TEXT, sdk_version TEXT
                  notifications_enabled BOOLEAN NOT NULL
                  os_version TEXT, device_model TEXT, locale TEXT, timezone TEXT
                  created_at, updated_at TIMESTAMPTZ

installation_tags installation_id UUID FK
                  key TEXT, value TEXT
                  PRIMARY KEY (installation_id, key)

installation_topics installation_id UUID FK
                  name TEXT
                  PRIMARY KEY (installation_id, name)

segments          id TEXT PK, name TEXT, description TEXT, rule JSONB
segment_members   segment_id TEXT FK, installation_id UUID FK, joined_at TIMESTAMPTZ
                  PRIMARY KEY (segment_id, installation_id)

events            id BIGSERIAL PK, installation_id UUID FK
                  name TEXT, occurred_at TIMESTAMPTZ, properties JSONB
```

### Indexes and constraints that matter

```sql
-- Targeting reads these constantly.
CREATE INDEX ON installations (application_id, user_id);
CREATE INDEX ON installations (application_id, notifications_enabled);
CREATE INDEX ON installation_tags (key, value);

-- See Step 9. Two installations must never hold the same live token.
CREATE UNIQUE INDEX ON installations (application_id, push_token)
    WHERE push_token IS NOT NULL;
```

**Done when:** you can insert an installation, move its token to another installation without
violating the unique index, and delete a user association without touching anything else.

## Step 2 — Cross-cutting middleware

Also before any endpoint. These behaviours are what the SDK's durable retry queue is written
against, and getting them wrong is silent data loss rather than a visible error.

### 2a. Read these headers

| Header | Example | Use it for |
| --- | --- | --- |
| `X-Application-Id` | `wallet_android` | Routing and validation. **Not** authentication |
| `X-Installation-Id` | `8f14e45f-…` | Correlation and logging |
| `X-Platform` | `android`, `ios` | Provider selection |
| `X-SDK-Version` | `1.0.0` | Compatibility triage |
| `X-App-Version` | `5.2.0` | Compatibility triage |
| `X-Request-ID` | UUID | **Idempotency and log correlation** — stable across retries of one logical request |
| `Authorization` | `Bearer …` | Authentication, when configured |

`X-Request-ID` is the useful one: the SDK generates it once per logical operation and **keeps it
across every retry**. Log it, and consider keying idempotency on it.

Header names are configurable client-side for gateways with another convention, so treat them as
configuration rather than constants if you sit behind such a gateway.

### 2b. Return this error shape

```json
{ "error": { "code": "invalid_token", "message": "Not valid for this application" } }
```

A bare `{"code": …, "message": …}` is also accepted by the client.

### 2c. Status codes — read this table twice

The SDK's entire retry policy is driven by your status code. This is verified against
`ApiResult.kt:48-58` in the client.

| You return | SDK does | Get it wrong and |
| --- | --- | --- |
| 2xx | Success, operation dropped from the queue | — |
| **400, 403, 404, 409, 422** | **Permanent. Dropped, never retried** | A transient failure sent as 400 is **lost forever** |
| **401** | One `AuthProvider` refresh, then one retry. Never loops | — |
| **408, 425, 429** | Retried with backoff | — |
| **5xx** | Retried with backoff | A permanent failure sent as 503 is retried until the budget runs out |
| Transport failure | Retried with backoff | — |

Two rules follow, and they are the ones teams get wrong:

- **A transient failure must never be a 4xx.** Database timeout, downstream unavailable, deploy in
  progress — all 5xx. A 400 tells the client to give up permanently.
- **A permanent rejection must never be a 5xx.** Unknown `applicationId`, malformed body, token
  the provider rejected — all 4xx. A 503 makes the client retry something that can never succeed.

Also: **a 2xx body the client cannot parse is treated as permanent.** A malformed success is a
contract violation, and retrying it forever would wedge the device's queue.

### 2d. Honour `Retry-After` on 429 and 503

Delta-seconds or an HTTP date. The client honours it, clamped to 15 minutes so a mistaken header
cannot park a device's queue. It is cheaper for both sides than the client guessing.

### 2e. Make every write idempotent

Every endpoint is retried by a durable client queue, so **every write will arrive more than
once.** Registration is keyed on installation id; token, identity, tag and topic writes are
merges or replacements, never deltas. There are no increment-style operations in this API, on
purpose.

**Done when:** a request replayed ten times leaves the database in the same state as one request,
and your error handler cannot return a 4xx for an infrastructure failure.

## Step 3 — `POST /v1/installations`

The root of everything. The SDK never sends a dependent operation before this has succeeded, and
nothing else can be tested until it works.

```json
{
  "applicationId": "wallet_android",
  "installationId": "8f14e45f-ea1e-4f7a-b2c1-5b2d7a1c9e33",
  "platform": "android",
  "provider": "fcm",
  "pushToken": "dGhpcyBpcyBhIHRva2Vu…",
  "userId": "USER_123",
  "appVersion": "5.2.0",
  "appBuild": "520",
  "sdkVersion": "1.0.0",
  "notificationsEnabled": true,
  "device": {
    "osVersion": "14",
    "deviceModel": "Google Pixel 8",
    "locale": "en-PK",
    "timezone": "Asia/Karachi"
  }
}
```

- **Upsert keyed on `installationId`.** The client generates it. Repeated identical calls must not
  create duplicates.
- `userId` is `null` when logged out.
- The whole `device` block is **absent** when the host set `collectDeviceInfo = false`. Do not
  require it.
- The client hashes the payload locally and skips the call when nothing changed, so repeated
  launches do not produce repeated writes. You will see fewer of these than you expect.

| Status | When |
| --- | --- |
| 200, 201 | Registered |
| 400 | Malformed body |
| 401 | Authentication required or expired |
| 422 | Unknown `applicationId`, or a token the provider rejects |

**Done when:** a real device running the sample app produces exactly one row, and a second launch
produces no second row.

## Step 4 — Token and identity

Build these next; they are the operations that keep the register truthful.

### `PUT /v1/installations/{id}/token`

```json
{ "token": "NEW_TOKEN", "provider": "fcm" }
```

Called on every token refresh, with no host involvement. **`provider` matters:** an APNs device
token and an FCM registration token are different values, and sending through the wrong one
reaches nobody.

`200`/`204` updated · `404` unknown installation — the SDK re-registers and retries, which
self-heals a pruned record · `422` provider rejected the token.

### `POST /v1/installations/{id}/identify`

```json
{ "userId": "USER_123" }
```

A user may own many installations. An installation belongs to **at most one user at a time** —
identifying replaces any previous association rather than merging.

### `DELETE /v1/installations/{id}/user`

Clears the user association and **nothing else.**

> This is the single most damaging endpoint to over-implement. If you unregister the device here,
> ARY can no longer reach that person with anything at all — including the win-back campaigns
> that logout exists to enable. Clear `user_id`. Leave the installation, the token and the tags.

`200`/`204` cleared · `404` already absent, treat as success.

**Done when:** logging out then in again on a real device leaves one installation row, with its
token and tags intact throughout.

## Step 5 — Tags, topics, reachability

### `PATCH /v1/installations/{id}/tags`

```json
{ "tags": { "subscription": "premium", "language": "en" } }
```

**A merge, not a replacement.** Absent keys keep their values. The SDK debounces and coalesces, so
a burst of `addTag` calls arrives as one request.

### `DELETE /v1/installations/{id}/tags`

| Query | Effect |
| --- | --- |
| `?keys=a,b,c` | Remove those keys |
| `?all=true` | Remove every tag |

### `PUT /v1/installations/{id}/topics`

```json
{ "topics": ["sports", "news"] }
```

**Replaces** the recorded set. Note the platform asymmetry:

- **Android** — FCM performs the fan-out. This call is bookkeeping so you can report on it.
- **iOS** — APNs has no topic concept, so **you perform the fan-out** and this call is the source
  of truth. Sending to a topic on iOS means looking up its subscribers and sending to each.

### `PATCH /v1/installations/{id}`

```json
{ "notificationsEnabled": false }
```

Mutable installation state; currently only reachability. Sent when the SDK notices the permission
state changed — **including the user turning notifications off in Settings, which the OS never
announces.** The SDK samples it at every launch and reports changes.

Suppress sends to installations where this is `false`. It keeps delivery rates honest and avoids
paying to send messages nobody can receive.

**Done when:** tags survive a partial update, `?all=true` clears them, and toggling notifications
off in system settings flips the flag on the next app launch.

## Step 6 — `GET /v1/installations/{id}/segments`

The only read endpoint the SDK calls. It backs `ARYPush.getSegments()`, so an app can branch on
membership without duplicating your rule.

```json
[
  {
    "id": "seg_premium_pk",
    "name": "Premium Pakistan Users",
    "description": "subscription == premium AND country == PK",
    "joinedAt": 1730000000000
  }
]
```

`{ "segments": [ … ] }` is also accepted, for gateways that wrap collections. `description` and
`joinedAt` are optional; `joinedAt` is epoch milliseconds. An entry without an `id` is skipped by
the client rather than failing the whole response.

`200` membership returned, possibly empty · `404` unknown installation — the SDK re-registers and
retries.

**The client does not cache this.** Membership changes on your side whenever tags change, and a
stale cached list is worse than a call the caller chose to make. Make it cheap rather than
expecting the client to call it rarely.

### Computing membership

```
Tags on an installation          Segment "Premium Pakistan Users"
  subscription = premium           subscription == premium
  country      = PK          -->   AND country == PK
  language     = en
```

Recompute when tags change. Targeting for campaigns happens entirely server-side; this read is a
convenience for the app, not something your campaign system should depend on.

**Done when:** adding a tag from the sample app changes what `getSegments()` returns on the next
call.

## Step 7 — `POST /v1/events`

```json
{
  "installationId": "8f14e45f-ea1e-4f7a-b2c1-5b2d7a1c9e33",
  "events": [
    {
      "name": "notification_opened",
      "occurredAt": 1730000000000,
      "properties": { "notificationId": "order-42", "actionId": "track" }
    }
  ]
}
```

The SDK emits `notification_received` and `notification_opened`.

`occurredAt` is epoch milliseconds and is the **client's** timestamp: an event queued offline
keeps the time it happened, not the time you received it. Do not overwrite it with server time —
store both if you need arrival time.

**Done when:** a device in airplane mode that receives and opens a notification reports events
with the original timestamps once it reconnects.

## Step 8 — Sending

You hold the credentials and you do the sending. Neither ever appears in an APK or an IPA.

| Platform | Credential | Where |
| --- | --- | --- |
| Android | FCM service account, HTTP v1 API | Your secret store |
| iOS | APNs auth key (`.p8`) or certificate | Your secret store |

### Send data-only messages

This is the one instruction in this document with the widest blast radius if ignored.

A data-only message is the **only** shape whose behaviour is identical across foreground,
background and terminated states, and across both platforms. A notification-payload message is
rendered by the OS before the SDK sees it, which loses deduplication, custom rendering, action
buttons and open tracking.

- **FCM:** send only the `data` block. Do not include `notification`.
- **APNs:** set `content-available: 1` and put your keys in the payload.

### Payload keys the SDK understands

```json
{
  "ary_push": "1",
  "notification_id": "order-42",
  "title": "Order shipped",
  "body": "Your order is on its way",
  "image_url": "https://cdn.ary.com/order.png",
  "channel_id": "orders",
  "action": "open_order",
  "orderId": "12345",
  "actions": "[{\"id\":\"track\",\"title\":\"Track\"}]"
}
```

| Key | Purpose |
| --- | --- |
| `ary_push` | Marks the message as the SDK's, so an app with its own messaging service can tell them apart |
| `notification_id` | **Stable identity. Always send it.** It is what makes deduplication work across resends |
| `title`, `body` | Content for data-only messages |
| `image_url` | Big-picture image |
| `channel_id` | Android channel; falls back to the SDK's own if it does not exist |
| `action` + your own keys | Delivered verbatim to the host app, which decides what to do |
| `actions` | JSON array of action buttons, as a **string** |

> The SDK never navigates. `action` and your custom keys are handed to the host application, which
> owns routing. Agree the `action` vocabulary with the mobile team and write it down — it is a
> contract between your campaigns and their code, and nothing will validate it for you.

**Done when:** a data-only message sent to one installation renders on the device, a resend with
the same `notification_id` does not render twice, and tapping it reaches the app's handler.

## Step 9 — Token uniqueness after a device restore

The rule that is easiest to skip and most annoying to debug.

A push token can **move between installations** after a device restore or an app reinstall. If two
installations end up holding the same token, that device gets **every message twice**.

On any registration or token update, before writing:

```sql
UPDATE installations SET push_token = NULL
 WHERE application_id = :app_id
   AND push_token = :token
   AND id <> :installation_id;
```

The newest registration wins; the older installation keeps its row and its history but loses the
token. The partial unique index from Step 1 enforces this even if the application code forgets.

**Done when:** restoring a backup onto a second device does not produce duplicate deliveries.

## Step 10 — Verify against a real device

The mobile SDK is finished, so you can test against the real client rather than a mock. Point the
sample app at your environment:

```kotlin
ARYPush.initialize(
    this,
    ARYPushConfig(
        backend = PushBackendConfig(
            baseUrl = "https://push-api-dev.ary.com",
            applicationId = "wallet_android"
        )
    )
)
```

### Acceptance checklist

| # | Do this | Expect |
| --- | --- | --- |
| 1 | First launch | One installation row, with token and device fields |
| 2 | Second launch, nothing changed | **No** second write — the client skips it |
| 3 | `login("USER_1")` | `user_id` set on the existing row, not a new row |
| 4 | `logout()` | `user_id` cleared; token, tags and row intact |
| 5 | `addTags(...)` rapidly | One coalesced `PATCH`, not one per call |
| 6 | Turn notifications off in system Settings, relaunch | `notifications_enabled` false |
| 7 | Airplane mode, add tags, reconnect | Queued writes arrive, with original ordering |
| 8 | Return 503 to a tag write | Client retries with growing backoff |
| 9 | Return 429 with `Retry-After: 30` | Client waits ~30s, not its own backoff |
| 10 | Return 404 to a token update | Client re-registers, then retries |
| 11 | Send the same `notification_id` twice | Rendered once |
| 12 | Restore the device onto a second handset | No duplicate deliveries |

Rows 8 to 10 are the ones worth doing deliberately with a fault-injection switch. They are the
paths that fail silently in production, and the only time they are cheap to test is now.

## Versioning, once you are live

Additive changes — new optional fields, new endpoints — stay within `v1`. Anything that **removes
a field, changes a type, or changes what a status code means requires `v2` served alongside
`v1`.**

A shipped mobile app cannot be asked to update on the backend's schedule. Old SDK versions stay in
the field for a long time: assume a year, and that some devices never update at all.

## Ordering you can rely on

```
POST   /v1/installations
PUT    /v1/installations/{id}/token
POST   /v1/installations/{id}/identify
PATCH  /v1/installations/{id}/tags
```

The SDK never sends a dependent operation before the installation exists. If one arrives first
anyway — a race you should still tolerate — answering **404 is correct**: the client re-registers
and retries.
